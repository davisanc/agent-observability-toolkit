Overview

The Agent 365 admin center gives you inventory and governance. The traces themselves (what users asked, which tools the agents called, how many tokens each answer cost) live in Azure Application Insights. This toolkit turns them into answers for platform and FinOps teams.

What was asked

  • Recent and most common prompts
  • Full conversation transcripts
  • Conversation length, prompt size, unanswered turns

What the agents did

  • Which tools each agent calls, and in what order
  • Arguments, results, latency and failures
  • Tool calls per prompt, new and vanished tools

What it cost

  • Tokens per agent, model, user and day
  • Estimated cost per prompt and most expensive prompts
  • Budget and spike alerts
Scope. This toolkit is for observability and cost. Security detections such as prompt injection and sensitive data in prompts are deliberately out of scope: use Microsoft Defender and Microsoft Purview DSPM for those.

A Log Analytics workspace uses AppEvents, AppDependencies and Properties. Every query is rendered for both and the copy buttons copy the one you selected. Run each version in the matching place. Most queries only call the helper functions, so they are identical in both schemas; the table names live in the functions.
What each platform can answer. Prompts and responses: all three, when content capture is on. Tool calls: Foundry, custom agents and Copilot Studio environment-level telemetry (preview), not Copilot Studio agent-level telemetry. Tokens: Foundry and custom agents that emit gen_ai.usage.*. Copilot Studio is licensed on messages or credits rather than tokens, so token cost is generally not available for it. Run V3 to see exactly what you have.

1. Connect telemetry

Use one workspace-based Application Insights resource for all agents in an environment, so a single set of functions covers everything. Prompt and tool content is only captured if you enable it. It is sensitive, so read section 8 first.

Copilot Studio

Agent-level telemetry (per agent)

  • Agent Settings → Advanced → Application Insights, paste the connection string.
  • Enable logging records incoming and outgoing messages and events.
  • Log conversation details adds user ID, user name and the message text.
  • Log sensitive Activity properties and Node execution events are optional.
  • Lands in customEvents as BotMessageReceived and BotMessageSend. Gives prompts and responses, not tool calls or tokens.

Environment-level telemetry (preview)

  • Configured centrally by an administrator, span-based and aligned with OpenTelemetry.
  • Lands in dependencies as invoke_agent, execute_tool and output_messages spans with gen_ai.* attributes, including tool arguments and results.
  • Managed environments only. Declarative agents are not included. Large content can be truncated.
  • This is the source for the Copilot Studio tool-call queries.

Content recording captures sensitive data. Microsoft's guidance is to enable it in development, and in production only where your compliance and privacy requirements allow it. Without it you still get spans, timings, tool names and token counts, which is enough for the tool and cost queries, but not the prompt text.

Custom agents on Azure Web Apps or Containers

Use the Azure Monitor OpenTelemetry distro and emit GenAI spans. Agent frameworks that already emit them (for example Semantic Kernel or Microsoft Agent Framework) only need configure_azure_monitor() and the connection string. For hand-built agents, this minimal pattern produces the spans the toolkit expects. Add a chat span per model call with gen_ai.usage.input_tokens and gen_ai.usage.output_tokens if you want token queries to work:

# pip install azure-monitor-opentelemetry
import json, os
os.environ["OTEL_SERVICE_NAME"] = "my-custom-agent-app"       # becomes cloud_RoleName / AppRoleName
os.environ["OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT"] = "true"   # only where policy allows
from azure.monitor.opentelemetry import configure_azure_monitor   # reads APPLICATIONINSIGHTS_CONNECTION_STRING
from opentelemetry import trace

configure_azure_monitor()
tracer = trace.get_tracer("my-custom-agent")

def handle_turn(conversation_id, user_id, user_text):
    # Default span kind (INTERNAL) lands in the dependencies table. SERVER spans would land in requests instead.
    with tracer.start_as_current_span("invoke_agent my-agent") as span:
        span.set_attribute("gen_ai.operation.name", "invoke_agent")
        span.set_attribute("gen_ai.provider.name", "azure.ai.openai")
        span.set_attribute("gen_ai.agent.name", "my-agent")
        span.set_attribute("gen_ai.conversation.id", conversation_id)
        span.set_attribute("enduser.id", user_id)                 # typically surfaces as user_AuthenticatedId
        span.set_attribute("gen_ai.input.messages",
            json.dumps([{"role": "user", "parts": [{"type": "text", "content": user_text}]}]))

        with tracer.start_as_current_span("execute_tool lookup_order") as tool:
            tool.set_attribute("gen_ai.operation.name", "execute_tool")
            tool.set_attribute("gen_ai.tool.name", "lookup_order")
            tool.set_attribute("gen_ai.tool.type", "function")
            tool.set_attribute("gen_ai.tool.call.arguments", json.dumps({"order_id": "123"}))
            result = {"status": "shipped"}                         # call your tool here
            tool.set_attribute("gen_ai.tool.call.result", json.dumps(result))

        with tracer.start_as_current_span("chat gpt-4o") as llm:   # one span per model call: this is what AgentTokens reads
            llm.set_attribute("gen_ai.operation.name", "chat")
            llm.set_attribute("gen_ai.request.model", "gpt-4o")
            answer = "Your order has shipped."                     # call your model here
            llm.set_attribute("gen_ai.usage.input_tokens", 812)    # take both from the model response's usage object
            llm.set_attribute("gen_ai.usage.output_tokens", 24)
        span.set_attribute("gen_ai.output.messages",
            json.dumps([{"role": "assistant", "parts": [{"type": "text", "content": answer}]}]))
        return answer

2. Save the helper functions

Four functions normalise every platform into one shape. AgentTraces: one row per prompt or response. AgentToolCalls: one row per tool call. AgentTokens: one row per model call with input and output tokens. AgentCost: AgentTokens priced with your own price table.

  1. Open Logs in the place that matches the table-name switch: the Application Insights resource for Application Insights names, or the Log Analytics workspace for Log Analytics names.
  2. Paste a function body below (it needs the lookback parameter, so it is not a runnable query by itself), choose Save → Save as function, name it exactly as shown, and add one parameter lookback of type timespan.
  3. Repeat for all four. Save AgentTokens before AgentCost, because AgentCost calls it.
  4. Edit the settings at the top of each: traceOps and customAgentRoles in AgentTraces, tokenOps in AgentTokens, and the price table in AgentCost.
Changes with the table-name switch. The helper functions are where the table names live. Use the version that matches where you save them.

If a query fails

Message or symptomLikely cause and fix
Failed to resolve table or column expression named AppEvents (or AppDependencies)The names do not match where you ran the query. The Logs blade of an Application Insights resource always uses the classic names (customEvents, dependencies), even when the resource is workspace-based. The App* names only exist in the Log Analytics workspace Logs. Run V1 in section 3: it works in either window and shows which table names exist where you are. Then switch the toggle to match.
Failed to resolve table or column expression named customEvents or dependenciesThe reverse: you are in the Log Analytics workspace. Switch the toggle to Log Analytics workspace.
Failed to resolve scalar expression named lookbackYou ran a function body directly. Save it as a function with a lookback timespan parameter, or use Copy as runnable query.
Failed to resolve table expression named AgentTraces, AgentToolCalls, AgentTokens or AgentCostThe function was saved in a different place. Functions saved in an Application Insights resource are not visible from the workspace, and the reverse. Save it where you run the query, or use Copy with functions inlined.
Unknown function: AgentTokens (or another helper) even though the definition is pasted above the queryA blank line splits a query in the Logs editor, and only the block under the cursor runs. Remove any blank lines between the let definitions and the query, or select everything before pressing Run. The copy buttons on this page (v2.0.1 and later) produce no blank lines.
Query runs but returns no rowsNo telemetry in the window, content capture is off, the platform does not emit that data, or tokenOps points at the wrong span type. Run V2 and V3.
Costs are all 0The price table in AgentCost still has placeholder prices, or the model names do not match. Run K8 and copy the names.

7. Operational alerts

These queries return rows only when something needs attention, so each one works as an Azure Monitor log search alert rule that fires when the number of results is greater than 0.

  1. Save the functions in the Log Analytics workspace that holds the Application Insights data and choose the Log Analytics workspace table names above. (Alerts on a workspace-based Application Insights resource itself can use the Application Insights names with functions saved there.)
  2. In the Azure portal open the workspace, then Alerts → Create → Alert rule. Choose the signal Custom log search and paste the query.
  3. Set Measurement to Table rows, Aggregation granularity equal to the frequency shown, and Alert logic to greater than 0. Add the split by dimensions shown on the card so you get one alert per agent.
  4. Set Evaluation frequency and the query window from the card. Azure Monitor limits how far back a log search alert can look, so the baselines here are deliberately short.
  5. Attach an action group (email, Teams, webhook), name the rule, and test with a lower threshold first.

8. Privacy and access

Observability traces can contain what employees and customers type into an agent. Treat the telemetry store as a sensitive data store, even though this toolkit does not look for sensitive content.

Content capture is optional

  • Without it you keep spans, timings, tool names and tokens, which is enough for sections 5 and 6 and the alerts.
  • Enable prompt and tool content in development and where policy allows in production.

Control who can read it

  • Anyone with read access to the workspace can read prompts. Use a dedicated workspace and restrict access with RBAC.

Retention and region

  • Choose a retention period per table that matches policy, and keep the resource in the region your data-residency rules require.

Involve the right people

  • Monitoring employee prompts can fall under works council, privacy or HR rules in some countries. Agree scope with your data protection officer first.
  • Per-user views (K6) are sensitive. Use them for chargeback only where agreed.
